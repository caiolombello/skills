# Maintain correspondence as code changes

Read the existing project check and its property, model/harness, assumptions/bounds, covered symbols/state writers, command/tool version, evidence and last correspondence revision. If there is no such record, establish the actual baseline and mark the missing history. Do not invent a prior pass or sync commit.

1. **Baseline:** run the current check when permitted, keeping its original inputs/result. A pass means that representation passes; it does not establish current code correspondence. Static-only scope preserves the runtime check as unrun.
2. **Inspect drift:** compare covered code from the last established correspondence to current source. Follow renames, moved/split functions, changed shared state, added writers/callers and external contracts. Classify changes by their effect on semantics, not commit-message reassurance or line count.
3. **Reconcile:** distinguish irrelevant textual changes, representation/harness drift, intended contract change with evidence, a possible product defect, and a coverage gap. A new path missing from the model is a gap even if all old checks pass.
4. **Update from source:** revise abstractions/harnesses to represent actual behavior, including atomicity, input domains and failure boundaries. Keep the existing promised property unless current authoritative intent establishes a change. Record old/new property and reason for any change. Report smaller bounds or additional exclusions; do not bury them in config.
5. **Run and challenge:** rerun affected properties and a meaningful negative variation where appropriate/authorized. For failures, replay or analyze the counterexample against the implementation. Do not edit product code during a maintenance-only task or document a real regression as desired behavior.
6. **Record correspondence and outcome:** advance the code-correspondence marker only for the source relation actually examined. Record pass, violation, incomplete run, unavailable tool and untested calibration separately. A correctly mapped model can have a real violation; this is different from stale correspondence. Never advance an aggregate green marker across unresolved gaps.

Useful per-check states are **in sync and checked**, **updated and checked**, **implementation violation**, **stale/coverage gap**, or **incomplete/unavailable**. These are independent dimensions when needed: a representation can be updated while still violating a property or while execution is unavailable. Explain that instead of forcing a single success label.

Keep verification-artifact changes separate from any separately authorized product correction. Preserve original failure evidence and the final checked snapshot. Use [verification-before-completion](../../verification-before-completion/SKILL.md) for general evidence/version reporting, and [receiving-code-review](../../receiving-code-review/SKILL.md) when triaging a finding. Do not start a recurring audit, publish or merge merely because maintenance was requested.
